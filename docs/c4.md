# C4 in Cartography

The [C4 model](https://c4model.com) describes software at four levels: the system landscape and system context, the containers inside a system, and the components inside a container. In Cartography you write the model once in YAML (`type: c4`) and draw each level as a view of it, the way Structurizr and LikeC4 work. Every view lays itself out; you never place a box by hand unless you want to.

The full example is [examples/c4/kestrel-bank.yaml](../examples/c4/kestrel-bank.yaml): online banking at a fictional bank, with a landscape, a context, a container, a component, a dynamic and a deployment view.

```sh
carto render examples/c4/kestrel-bank.yaml --all-views          # one SVG per view
carto render examples/c4/kestrel-bank.yaml --view containers --format png
carto new c4 shop.yaml                                          # a starter
```

## The model

```yaml
type: c4
title: Kestrel Online

elements:
  customer: { kind: person, label: Personal customer, description: Holds accounts at Kestrel Bank }
  online:
    kind: software-system
    label: Kestrel Online
    description: Lets customers check balances and move money
    elements:                                    # containers, addressed as online.web, online.api
      web: { kind: web-app, label: Web banking, technology: Next.js, description: Serves the banking site }
      api:
        kind: container
        label: Banking API
        technology: Spring Boot
        elements:                                # components, addressed as online.api.signin
          signin: { kind: component, label: Sign-in controller, technology: Spring MVC }
      db: { kind: database, label: Customer store, technology: PostgreSQL 16 }
  mail: { kind: software-system, label: Postbird, external: true, description: Sends transactional email }

relations:
  - customer -> online.web: { label: Banks online, technology: HTTPS }
  - online.web -> online.api: { label: Calls, technology: JSON/HTTPS }
  - online.api.signin -> online.db: { label: Reads logins, technology: JDBC }
  - online.api -> mail: Sends email
```

- **Nesting is the level.** A top-level element is a person or software system, its `elements:` are containers, theirs are components. Without a `kind:` an element gets the kind its depth means, so a quick model needs no kinds at all.
- **Kinds**: `person`, `software-system`, `container`, `component`, and the container variants `web-app`, `mobile-app`, `desktop-app`, `database`, `queue`, `storage`. Each has its own icon; the card says what it is the C4 way: `[Container: Spring Boot]`.
- **`description`** is written in the card, wrapped to at most three lines. Keep it to one sentence.
- **`external: true`** (or `tags: [external]`) marks something outside your scope: external systems are drawn greyed, and external people and systems stay outside an enterprise boundary.
- **`technology`** on a relation is drawn after its label, quieter: `Calls [JSON/HTTPS]`. `style: async` draws a dashed line.
- Words from the architecture type work too (`system`, `service`, `api`, `client`, `db`, `topic`, …): they map to the C4 kind, so one model can feed both.

## Views

Each view says what kind of C4 diagram it is and what it is about; it picks its own elements.

```yaml
views:
  landscape: { kind: landscape, enterprise: Kestrel Bank }
  context: { kind: context, of: online }
  containers: { kind: container, of: online }
  components: { kind: component, of: online.api }
```

| `kind:` | Shows |
|---|---|
| `landscape` | Every person and software system. `enterprise: Name` draws the ones that are not external inside a dashed enterprise boundary. |
| `context` | The system `of:` and every person and system with a relation to it or to anything inside it, all closed. |
| `container` | The system opened into a dashed `[Software System]` boundary with its containers, plus the people and systems they talk to. |
| `component` | The container opened into a `[Container]` boundary inside its system, with the sibling containers and outside elements its components talk to. |
| `dynamic` | Only the numbered `steps:`, between the elements they name, inside the boundaries they belong to. |
| `deployment` | Deployment `nodes:` as nested boxes with instances of model elements. |

- Relations are drawn at the level shown: `customer → online.web` is drawn as `customer → online` in a context view (C4's implied relationships). When a relation is written between exactly the two elements shown, its label is used instead of the implied ones.
- `include:`, `exclude:` and `expand:` still work on top of what the kind picks, e.g. `exclude: [online.worker]` or `include: [tag:partner]`. `title`, `subtitle` and `direction` too.
- **Drill-down**: a card links to the next view about it. In the landscape, Kestrel Online links to its context; in the context to its containers; in the container view the Banking API links to its components. SVGs from `--all-views` link to each other; in the editor ⌘-click follows the link.
- **Legend**: every view gets one automatically: the element types it shows (person, software system, external system, container, database, …), boundaries and the kinds of line.

### Dynamic views

```yaml
  payment:
    kind: dynamic
    title: Making a transfer
    steps:
      - customer -> online.app: Confirms a transfer
      - online.app -> online.api.payments: { label: Submits it, technology: JSON/HTTPS }
      - online.api.payments -> online.api.ledger: Books it
      - online.api.ledger -> ledger: { label: Posts the booking, technology: ISO 20022 }
```

Each step is drawn as its own line with its number in a small circle, and the steps are listed under the drawing. Steps may name elements at any level; the boundaries they sit in are drawn for you. In the graph each step is kept as `{ n, edge, from, to, label }` (`Graph.steps`), which is what a step-through presentation walks.

### Deployment views

```yaml
  production:
    kind: deployment
    title: Kestrel Online — production
    nodes:
      phone: { label: Customer's phone, technology: iOS or Android, instances: [online.app] }
      aws:
        label: Amazon Web Services
        technology: eu-west-1
        nodes:
          lb: { kind: load-balancer, label: Load balancer, technology: ALB }
          eks:
            label: EKS cluster
            technology: Kubernetes 1.31
            nodes:
              api-pods: { label: banking-api, technology: Docker, count: 4, instances: [online.api] }
          rds: { label: Amazon RDS, technology: PostgreSQL 16, instances: [online.db] }
    edges:
      - lb -> online.api: { label: Forwards, technology: HTTPS }
```

- Deployment nodes nest with `nodes:` and are drawn as boxes captioned `[Deployment Node: Kubernetes 1.31] ×4` (`count:`).
- `instances:` places model elements (containers or software systems) in a node. A node with neither nodes nor instances is an infrastructure node: `load-balancer`, `gateway`, `firewall`, `dns`, `cdn` or plain `infrastructure`.
- The model's relations are drawn between the instances (a relation of a component is drawn from the container it runs in). An element deployed in two environments is drawn twice (`online.api@eu`, `online.api@us`), and its instances talk to the instances in their own environment.
- `edges:` adds lines between nodes or instances (`lb -> online.api`); one written here wins over the model's relation between the same two.
- `of:` on a node is the short form for a managed service that is the element: `rds: { of: online.db, technology: Amazon RDS, count: 2 }` draws one card with the element's name, captioned `[Container: Amazon RDS] ×2`, instead of a box with one card in it. An id that is not in the model is a warning.
- `complete: true` on the view warns about every container that is in no `instances:` and that no node is `of:`; `complete: [online.api, online.db]` checks only those. People and external systems are not expected to be deployed.
- For a deployment drawn with real Azure or Kubernetes icons, use an `azure` (or `kubernetes`) diagram that includes the model and references elements with `ref:`; see [model.md](model.md) and [examples/model/deployment.yaml](../examples/model/deployment.yaml).
- For AWS or Google Cloud, several instances of one container, or one file with dev, test and production, use `of:` and `env:` in a `cloud`, `azure` or `kubernetes` diagram; see [Deployments](model.md#deployments-of-what-a-resource-runs) and [examples/deployment](../examples/deployment).

A `type: model` file whose views have a `kind:` is drawn in C4 notation too.

## From Structurizr DSL

A Structurizr workspace maps closely onto one `type: c4` file with its views. Your own AI converts one well with this table at hand ([ai.md](ai.md)); styles, themes, properties and perspectives have no counterpart (the C4 look is built in).

| Structurizr DSL | Cartography (`type: c4`) |
|---|---|
| `workspace "Name"` | `title: Name` |
| `u = person "Customer" "Desc"` | `elements: { u: { kind: person, label: Customer, description: Desc } }` |
| `s = softwareSystem "Shop" "Desc" { … }` | `s: { kind: software-system, label: Shop, description: Desc, elements: { … } }` |
| `c = container "API" "Desc" "Java"` | `c: { kind: container, label: API, technology: Java, description: Desc }` inside `s.elements` |
| `container … "Database"` tag | `kind: database` (also `queue`, `web-app`, `mobile-app` by tag or technology) |
| `component "Ctrl" "Desc" "Spring MVC"` | `kind: component` inside the container's `elements` |
| `u -> c "Uses" "HTTPS"` | `relations: [ u -> s.c: { label: Uses, technology: HTTPS } ]` |
| `enterprise "Bank" { … }` | `views: { landscape: { kind: landscape, enterprise: Bank } }`; what is outside gets `external: true` |
| `tags "External"` / location external | `external: true` |
| `systemLandscape key { include * }` | `key: { kind: landscape }` |
| `systemContext s key` | `key: { kind: context, of: s }` |
| `container s key` | `key: { kind: container, of: s }` |
| `component s.c key` | `key: { kind: component, of: s.c }` |
| `dynamic s key "Title" { a -> b "Does" }` | `key: { kind: dynamic, title: Title, steps: [ a -> b: Does ] }` |
| `deploymentEnvironment "Live" { deploymentNode … }` + `deployment s "Live" key` | `key: { kind: deployment, nodes: { … } }` |
| `deploymentNode "EKS" "" "Kubernetes" "" 3` | `eks: { label: EKS, technology: Kubernetes, count: 3, nodes: { … } }` |
| `containerInstance c` | `instances: [s.c]` |
| `infrastructureNode "LB" "" "ALB"` | `lb: { kind: infrastructure, label: LB, technology: ALB }` |
| `autoLayout lr` / `tb` | `direction: right` / `down` (layout is always automatic) |
| `include` / `exclude` expressions | the view kind picks elements; add `include:` / `exclude:` rules for the rest |
| `styles { element "Person" { … } }` | not needed: kinds bring the C4 look; brand themes change colours and fonts |

LikeC4 and IcePanel users will recognise the same ideas: elements nested in a model, relations between any two levels, views that pick what to show and link to each other.
