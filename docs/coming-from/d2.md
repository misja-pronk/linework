# Coming from D2

D2 and Cartography both start from text and both care about how the result looks. The difference is in what the text says: in D2 you describe shapes and connections and pick their look; in Cartography you say what each thing *is* (a service, a database, a subnet, a table) and the type and theme decide how it is drawn.

## Bring your diagrams

```sh
carto import shop.d2             # → shop.yaml (and shop-tables.yaml, one file per extra diagram)
carto import docs/README.md      # every ```d2 block (and ```mermaid, ```plantuml) in a Markdown file
carto render shop.yaml -f svg    # like d2 shop.d2 shop.svg
carto watch shop.yaml            # like d2 --watch
```

In the editor: drop a `.d2` file on the window, or paste D2 in the start dialog (*Import from Mermaid, D2, PlantUML…*). The drawing appears before you open it, with a list of what was left out. Nothing is fetched: the parser is Cartography's own and icons are read as words, never downloaded.

One D2 file can become several diagrams, because Cartography has a type for each kind of picture:

| In the D2 file | Becomes |
| --- | --- |
| Shapes, containers and connections | `type: systems`; `type: cloud` with `provider: aws`, `gcp` or `azure` when the icons (icons.terrastruct.com) or a container called AWS, Google Cloud or Azure say so, with the products as kinds (Lambda, S3, RDS, SQS, CloudFront, Cloud Run, BigQuery, …) |
| `shape: sql_table` | `type: erd` with the columns, `constraint: primary_key / foreign_key / unique` as `pk`, `fk`, `unique`, and `orders.customer_id -> customers.id` as the foreign key. In the architecture a table (or the database that holds the tables) is one database box |
| `shape: class` | `type: class`: each field and method a member (`+reader: io.RuneReader`, `peek(): (r rune, eof bool)`; no sign is public), connections as associations. Beside other boxes a class is a box in the architecture too, and the classes come in as a class diagram of their own |
| `shape: sequence_diagram` | `type: sequence`: actors in order, messages in order, groups as frames (a group called `loop …`, `alt …`, `opt …` or `par …` is that frame), notes on actors; a dashed connection is a reply |
| `steps` | `steps:` that build the drawing up: the first shows the main board, each next one shows what that step adds |
| `scenarios` | `views:` of one file: the main board, and one per scenario with what it adds |
| `layers` | a diagram of their own each |

What the import reads and what it does with it:

- **Kinds** come from the shape (`person`, `cylinder`, `queue`, `stored_data`, `cloud`), then from the words of the label and the icon's file name: "Orders DB" is a database, a cylinder called "Redis cache" is a cache, an icon `aws/Compute/AWS-Lambda.svg` is a Lambda function.
- **Containers** become groups with `in:`; their kind comes from their name (VPC, subnet, region, cluster, …). Dot paths (`a.b.c`), `_` for the parent and connections written inside a container all resolve to the same ids.
- **Connections**: `->`, `<-` (turned round), `<->`, `--`, chains (`a -> b -> c: label`, the label on each), labels in the connection's block. A dashed or animated line (`style.stroke-dash`, `style.animated`) is `style: async`; in a cloud diagram, which has no async style, `line: dashed`.
- **Text**: quoted keys, `|md …|` and `||…||` block strings (the first line, without markup), `#` comments, `"""` block comments, `;` between statements. A text near the top (`near: top-center`) is the title.
- **vars** are filled in, nested ones too (`${db.name}`); a variable that is not set is said, and `vars.d2-config` (D2's theme and layout engine) is left out with a warning.
- **Cloud products** by their names or icons: inside a group named after AWS, Azure or Google Cloud, `Front Door`, `Cosmos DB`, `Transit Gateway` or `Cloud Armor` become that provider's kind.
- `x: null` removes x and its connections.
- `direction:` is kept; `up` is drawn down and `left` right.

## What maps to what

| D2 | Cartography |
| --- | --- |
| `direction: right` | `direction: right` |
| `api: Orders API` | `api: { kind: service, label: Orders API }` under `nodes:` |
| `db: Orders DB {shape: cylinder}` | `db: { kind: database, label: Orders DB }`: the kind brings the shape and the icon |
| `q: Events {shape: queue}` | `kind: queue` (or `topic`, `event-stream`) |
| `u: Customer {shape: person}` | `kind: user` |
| `cloud: AWS { vpc: VPC { … } }` | `groups:` with `in:`; in a `cloud` diagram the group kinds are `account`, `vpc`, `subnet`, … |
| `a -> b: label` | `- a -> b: label` under `edges:` |
| `a -> b {style.stroke-dash: 3}` | `- a -> b: { style: async }`, a line kind with its own dash, named in the key |
| `a.b -> c.d` (paths into containers) | `- b -> d`: ids are unique in the file, groups are said with `in:` |
| `x: {shape: sql_table; id: uuid {constraint: primary_key}}` | `type: erd` with `tables:`, a column as `id: uuid pk` or `customer_id: uuid fk customers` |
| `shape: sequence_diagram` | `type: sequence` |
| `layers`, `scenarios`, `steps` | `views:` (what one drawing shows of the model) and `steps:` (a drawing told in parts) |
| `classes`, `style.fill` | themes and brand themes, not per box |
| `--layout elk` / `tala` | one layout per type, nothing to choose |
| `near: top-center` title | `title:` and `subtitle:` |
| `icon: https://…` | `kind:` picks a built-in icon; an icon pack adds your own (no URLs fetched) |

## The same diagram, both ways

```d2
direction: right
customer: Customer {shape: person}
shop: Web shop {
  web: Storefront
  api: Orders API
  db: Orders DB {shape: cylinder}
}
customer -> shop.web: HTTPS
shop.web -> shop.api: REST
shop.api -> shop.db: SQL
```

```cartography
type: systems
title: Web shop
groups:
  shop: { kind: system, label: Web shop }
nodes:
  customer: { kind: user, label: Customer }
  web: { kind: client, label: Storefront, in: shop }
  api: { kind: service, label: Orders API, in: shop }
  db: { kind: database, label: Orders DB, in: shop }
edges:
  - customer -> web: HTTPS
  - web -> api: { label: REST, style: sync }
  - api -> db: { label: SQL, style: data }
```

## What you lose

- **Free-form drawing.** D2 lets you put any shape anywhere, style it, nest markdown and code in it, and pick between three layout engines. Cartography only draws what a type knows, in its theme.
- **TALA and grid layouts.** There is one layout per diagram type. You can drag things in the editor and the position is kept, but there is no `grid-columns`.
- **What the importer leaves out**, each said in its report: styles (`style.*`), `classes` and `class`, sizes and positions (`width`, `height`, `top`, `left`), grids, `near` (except a title), tooltips and links, arrowhead shapes, globs (`*.style.fill`), edge references (`(a -> b)[0]`), imports (`...@file`), text, code, markdown and image shapes, spans in sequence diagrams (activations follow the calls instead), constraints other than keys and unique, and links between layers. What a step or a scenario changes or removes is not kept apart, only what it adds.
- **Sketch mode, animated SVGs and per-object classes.**

## What you gain

- **Meaning in the file.** `kind: database` on an Azure diagram becomes an Azure SQL icon, a key entry and a check that it sits in a subnet; the same file can be drawn as a context, container or deployment view ([model.md](../model.md)).
- **Types that know their subject**: Azure, AWS and Google Cloud, Kubernetes, networks with VLANs and IP plans, ERDs, access and roles, GitHub organisations, roadmaps, journeys, capability maps, RACI and CRUD matrices, threat models.
- **Importers from what you have**: Terraform, Azure Resource Graph and Bicep, Kubernetes manifests and Helm charts, Docker Compose, OpenAPI, AsyncAPI and GitHub Actions ([from a code repository](../repo-import.md)), Entra and GitHub exports, Structurizr, draw.io.
- **Stable edits and diffs** in pull requests ([ci.md](../ci.md)), and an editor where you can drag, build without YAML and present step by step.
- See the [layout benchmark](../benchmark.md) for D2 with dagre, ELK and TALA next to Cartography, including where D2 does better.
