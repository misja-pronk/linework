# Gap review: what stands between Linework and "demolish the competition, for free"

As of 2026-11-09. Input: README, requirements, market-2026-11 and its notes, the comparison page, and the current code (6 types: azure, erd, access, github, data-products, systems; CLI `types/new/validate/import/render/watch`; web editor with Describe/Build/YAML, Mermaid import, multi-select, folder editing, SVG/PNG/16:9 export).

**Verdict.** The core is already better than the free field: layout quality, two-way builder, and typed niche diagrams. What is missing is almost all **reach** (Linework isn't yet in the places diagrams live: PRs, docs, IDEs, agents) and **one-model thinking** (views, links, steps). Mermaid wins on being everywhere, not on quality. We beat it by being everywhere too, and better.

## 2. Table stakes we lack vs differentiators we could own

**Table stakes (users expect these; without them they won't try us):** npm/embed package, Markdown & docs-site rendering, VS Code preview, PDF, brand themes, K8s + network types, share link, accessible SVG (title/desc, keyboard canvas, AA contrast checked), performance at 200+ nodes off the main thread, a docs site with a gallery, `npx` that just works with no headless Chrome.

**Differentiators no free tool does well (lean on these in launch copy):**
1. **Diagrams that hold still**: stability-scored layout + sidecar pins + CI drift check. Measurable, shown on a benchmark page.
2. **Visual PR diff**: before/after with changed elements highlighted, posted by an Action. Nobody does this.
3. **Domain types that understand the domain**: data-mesh maps from ODPS/ODCS, Entra access packages with four views, GitHub org design. Every rival has generic boxes only.
4. **Generated, then curated**: importers that merge into existing YAML and keep pins on re-import. Generators (Hava, TerraVision) always redraw from scratch.
5. **Agent-native**: an MCP server that validates, renders and *returns layout-quality diagnostics*, so the agent fixes its own diagram. Combined with the existing "Describe it" flow.
6. **Serverless sharing**: the whole diagram compressed in the URL fragment, opened read-only in the static app, with comments carried in the same link. Free with no backend, which a SaaS rival can't match on privacy.
7. **Slide-ready by default**: 16:9 frames, brand themes and step-through in one offline tool.

## 3. Nine build rounds

Rule: workstreams in one round touch disjoint packages. To keep that possible, **importers live in their type package** (`types/<t>/src/import/`), and `packages/import` stays Mermaid-only. New capabilities get new packages (`embed`, `mcp`, `action`, `vscode`, `docs`).

| # | Workstream A | Workstream B | Workstream C | Why this order |
|---|---|---|---|---|
| 1 | **Embed**: `packages/embed`: browser render bundle, `<linework-diagram>` web component, npm-ready exports | **Stability**: stability term in the scorer + `linework validate --drift` (`layout`, `cli`) | **MCP + skill**: `packages/mcp` (schema, validate, render, layout diagnostics, examples), Claude skill, `llms.txt` | Everything later builds on embed; stability is the core promise; MCP is cheap reach |
| 2 | **GitHub Action**: `packages/action`: render on push, before/after PR comment with changed elements highlighted | **Brand themes**: theme file (tokens, font, logo, title block), `--theme client.json` (`theme`, `render`) | **Share link + read-only viewer** (URL fragment, no server) (`web`) | Git-native story and consultant story both become demoable |
| 3 | **Data wedge**: ODPS import, ODCS 3.1 relationships, focus/N-hop view (`types/data-products`) | **PDF + multi-page export** (`render`, `cli`, via resvg/pdf-lib) | **Performance**: layout in a web worker, 200-node budget in CI (`web`, `engine`) | Launch wedge is ready by round 3; perf before the big types land |
| 4 | **Kubernetes** type + manifests/Helm/kustomize importer, app vs full view (`types/kubernetes`) | **Access importers**: az role assignments, AzureHound, Entra packages; GitHub REST teams/repos (`types/access`, `types/github`) | **Docs plugins**: remark/markdown-it, MkDocs, Docusaurus, Kroki-compatible endpoint (new `packages/docs-plugins`) | Fills the biggest type gap; makes access an audit tool |
| 5 | **VS Code extension**: preview, schema, builder webview, auto-registers MCP (`packages/vscode`) | **ERD importers**: SQL DDL (Postgres/MySQL), DBML, Prisma + subset view (`types/erd`) | **Networking** type (zones/CIDR buses, devices), optional NetBox import (`types/network`) | Developer adoption plus the two oldest type requests |
| 6 | **One model, many views**: includes, shared element catalogue, `views:`, cross-diagram links and drill-down (`core`, `engine`) | **Terraform plan / Bicep / ARM importer** keeping pins (`types/azure`) | **Accessibility** in the editor: keyboard canvas navigation, focus order, screen-reader outline, reduced motion (`web`) | The big architectural change happens once the plumbing is stable |
| 7 | **Storytelling**: `steps:` (reveal, highlight path, captions), presentation mode, step export to PDF/slides (`render`, `web`) | **Git flow** type with presets (Git Flow, GitHub Flow, trunk), optional `git log` import (`types/gitflow`) | **Interop**: draw.io + Excalidraw import/export, Mermaid export (new `packages/interop`) | Steps need the model from R6; interop lowers the switching cost before launch |
| 8 | **Developer journey** type, steps linked to architecture nodes, uses `steps:` (`types/journey`) | **Comments without a server**: sidecar `<name>.comments.json`, pins on elements, carried in the share link, surfaced in the PR Action (`web`, `action`) | **SVG accessibility + semantics**: title/desc, roles, alt text from the model, AA contrast check in tests (`render`, `theme`) | Unique types that need the model; collaboration covers the review loop |
| 9 | **Docs site + gallery + benchmark page** (Mermaid/D2-TALA/PlantUML/Linework scored on crossings, bends, displacement after one edit) (`docs/site`) | **Launch assets**: Show HN post, 60-s video, "coming from Mermaid / D2 / Structurizr" guides, ODCS/Bitol listing request, README hero (`docs`, `README`) | **Release hardening**: npm publish pipeline, licence check, e2e on all templates, versioned schemas on a stable URL (`.github`, root) | Launch-ready free product |

**Placed:** every planned candidate above. **Rejected or deferred:**
- Live multi-user editing and a hosted SaaS with accounts. They break "free, offline, private"; the share link plus comments cover 80% of the need.
- Live cloud scanning with credentials. Import the JSON the user's own CLI produced (`az`, `kubectl`, `terraform show -json`) instead: no keys, no network, same staleness payoff.
- A D2/Structurizr importer. Wait for demand after the "coming from" guides in round 9.
- A Kroki endpoint. Ship it only as a thin wrapper inside docs plugins (round 4), not as a server product.

**Watch-outs.** LikeC4 (MIT, near-daily releases) already has dynamic-view walkthroughs, an MCP server that renders inline, a VS Code extension and web components. Rounds 1, 5 and 7 must match it, not just exist. Our moat against it is the domain types, the visual PR diff and the look. Pick one launch wedge (data mesh, round 3) and keep the round-9 story on it rather than listing nine types.
