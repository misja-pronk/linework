# Definitive scope: what Linework must draw, and in what order

As of 2026-11-09. Builds on [market-2026-11](market-2026-11.md) and [gaps-2026-11](gaps-2026-11.md), and replaces the gaps plan's round table (§3) as the build order. The test for every item is the same: **does a cloud/data architect-consultant draw this for clients, slides, docs or repos at least a few times a year?** If yes, it is in scope. If it is a whiteboard, BI or code-generation job, it is not.

**The key structural decision.** Linework should not grow 25 independent types. It needs four shared engines, and most diagram kinds are then a thin type or a view on top of one of them:

| Engine | Exists? | Serves |
|---|---|---|
| **Graph** (dot placement + own orthogonal router) | yes | systems/C4, Azure, AWS/GCP, K8s, network, GitHub, access graph, data products, ERD, states, threat model, context map |
| **Matrix** (rows × columns) | yes (`render/matrix.ts`) | access views, RACI, CRUD, product × consumer |
| **Lanes + axis** (participants/lanes × ordered steps or time) | **missing** | sequence, git branching, delivery pipeline, roadmap/timeline, developer journey, swimlane process |
| **Tree / pack** (nested boxes, tidy trees) | **missing** | capability map, team topologies/org chart, (mind map later) |

Above the engines sits a **model layer** (shared elements, views, links, steps), also missing. C4, deployment views, dynamic views, drill-down and step-through all depend on it, which is why it moves from round 6 in the gaps plan to round 1 here.

## 1. Diagram type catalogue

Legend: **M** must, **S** should, **X** skip. "Type" = new `types/<name>` package; "view/mode" = a `view:`, `notation:` or overlay of an existing type.

Result: 6 existing types, 9 new (`sequence`, `kubernetes`, `network`, `roadmap`, `gitflow`, `journey`, `cloud`, `process`/`states`, `teams`/`capabilities`/`matrix` as small ones), plus C4, deployment, dynamic, lineage, threat, context-map as views or modes.

## 3. Build backlog: 8 rounds × 3 workstreams

Rules carried over from the gaps plan: workstreams in a round touch disjoint packages; importers live in their type package; new capabilities get new packages. Every new type ships with JSON Schema, builder palette, ≥ 3 templates, gallery examples, layout-quality guard and a light + dark snapshot. "Done" also means: renders identically in CLI and web, exports to SVG/PNG/PPTX/PDF once those exist.

Ordering principle: first what the owner needs in his next client deck (model/C4, branding, official icons, PPTX/PDF, sequence), then the remaining must-have types on the new engines, then reach and import, then the should-haves.

### Round 1: foundations the owner uses daily
- **A. Model and views** (`core`, `engine`). Goal: one model, many diagrams. Accept: `include:` of other YAML files; a shared `elements:` catalogue referenced by id across files; `views:` with include/exclude/expand rules; `links:` on any element (URL, file, `diagram#view`); pins stored per view; existing six types unchanged and their snapshots identical.
- **B. Brand themes and BYO icon packs** (`theme`, `icons`, `render`). Goal: output looks like the client's deck. Accept: `--theme acme.json` and `theme:` in YAML with palette, fonts, logo, title block; contrast check fails below AA; `linework icons add <folder>` indexes an official Azure/AWS/GCP SVG pack into a user cache with a kind→icon map; icons render unrecoloured and unstretched; nothing from those packs lands in the repo or npm package.
- **C. MCP server and agent kit** (new `packages/mcp`). Goal: agents write correct diagrams first time. Accept: tools `list_types`, `get_schema`, `validate`, `render` (SVG/PNG), `layout_report` (crossings, bends, overlaps); resource with examples per type; Claude skill and `llms.txt`; schemas published at a versioned URL; tested from Claude Code against three prompts per type.

### Round 2: C4, client-ready export, sequence
- **A. C4 notation and views on `systems`** (`types/systems`). Accept: kinds person, software-system, container, component, external, database, queue; landscape/context/container/component views generated from one model; C4 legend and technology captions; Internet Banking reference example renders all four levels with drill-down links.
- **B. PPTX and PDF export** (new `packages/export`, `cli`, `web` export menu). Accept: PPTX uses native shapes, text boxes and elbow connectors that stay attached when moved in PowerPoint (fallback: SVG picture), one slide per view, brand title block; vector PDF multi-page with working links; opens cleanly in PowerPoint, Keynote and Google Slides.
- **C. Lanes engine + `sequence` type** (new `packages/lanes`, `types/sequence`). Accept: participants from the model or inline; sync/async/reply/self messages, activations, fragments `alt/opt/loop/par/break` with nesting, notes, auto-numbering, participant groups; no overlapping labels at 30 messages; OAuth code flow and saga templates; Mermaid `sequenceDiagram` import.

### Round 3: infrastructure types and editor craft
- **A. `kubernetes` type + importer** (`types/kubernetes`). Accept: cluster → namespace → workloads, Service/Ingress/Gateway, config, storage, identity, policy, HPA; app view vs full view; import from `kubectl -o yaml`, `helm template`, `kustomize build` that merges into existing YAML and keeps pins; AKS baseline template.
- **B. `network` type** (`types/network`). Accept: zones/segments with CIDR, devices, buses (nwdiag style), VPN/ExpressRoute/peering styles, per-device IP/port table view; hub-spoke with Azure Firewall and private DNS template; CIDR overlap warning.
- **C. Editor craft and keyboard canvas** (`web`). Accept: align/distribute (6 + 2 ops), snap to grid, manual bends saved in sidecar, arrow-key nudge, arrow/Tab navigation between elements with visible focus, command palette lists every action with shortcut, find element (`⌘F` on canvas); e2e tests per action.

### Round 4: time and flow on the lanes engine, plus CI
- **A. `roadmap` type** (`types/roadmap`). Accept: workstreams as lanes, items by date/quarter/sprint, phases, milestones, dependencies routed between items, today line, baseline vs plan; fits 16:9 automatically; 12-month migration and data-platform roadmap templates.
- **B. `gitflow` type with `delivery` view** (`types/gitflow`). Accept: presets Git Flow, GitHub Flow, trunk-based, release branches; commits, merges, tags, PR annotations; delivery view with stages, gates, approvals and environments; optional `git log --format` import; Mermaid `gitGraph` import.
- **C. GitHub Action + stability** (new `packages/action`, `layout`). Accept: renders changed diagrams on push and commits or uploads SVG; PR comment with before/after and changed elements highlighted; displacement term in the scorer keeps the previous winner unless clearly better (lab shows < 10% node movement after adding one edge on all examples); `linework validate --drift` fails on stale pins.

### Round 5: storytelling, deployment, reach
- **A. Steps and presentation mode** (`render`, `web`, `export`). Accept: `steps:` with reveal, highlight path, dim others, caption; C4 dynamic views compiled to steps or to a sequence diagram; full-screen presenter with arrow keys; each step exports as PPTX slide / PDF page.
- **B. `cloud` type (AWS, GCP) + deployment views** (`types/cloud`, `types/azure`). Accept: ~40 kinds per provider with Lucide fallbacks and BYO official icons; `of: <model-id>` places model elements into infra groups of azure/cloud/kubernetes; deployment view per environment from one model.
- **C. Embed and docs plugins** (new `packages/embed`, `packages/docs-plugins`). Accept: `<linework-diagram src>` web component with zoom and link drill-down; remark/markdown-it plugin turns ```` ```linework ```` blocks into inline SVG at build time; MkDocs and Docusaurus examples; no headless browser anywhere.

### Round 6: journey, data wedge, access audit
- **A. `journey` type** (`types/journey`). Accept: persona, phases, steps with touchpoints linked to model elements (click goes to the architecture view), emotion curve, pains/gains; uses `steps:`; developer onboarding and "first deploy" templates.
- **B. Data wedge** (`types/data-products`, plus core focus view). Accept: ODPS v1 import (products, ports), ODCS 3.1 `relationships` in detail view, focus/N-hop lineage view usable by every graph type; `linework render` of a folder of ODPS/ODCS files yields a data-mesh map in one command.
- **C. Access and GitHub importers** (`types/access`, `types/github`). Accept: `az role assignment list`, Graph JSON for groups and access packages, AzureHound JSON, GitHub REST teams/repos/rulesets; merge keeps pins; diff of two imports renders "gained / lost access" highlighting.

### Round 7: should-have types and interop
- **A. Tree/pack engine + `capabilities` and `teams`** (new `packages/tree`, two types). Accept: capability map with levels 1–3 and heatmap overlay with legend; org chart (tidy tree); Team Topologies shapes and interaction modes; all fit 16:9.
- **B. `process` and `states` types** (lanes and graph engines). Accept: swimlanes per role, tasks, xor/and gateways, start/end/timer/message events; states with initial/final, composite, guards; access-request process and order lifecycle templates; Mermaid `stateDiagram` import.
- **C. Interop** (new `packages/interop`). Accept: `.drawio` export that is editable in draw.io (shapes, groups, connectors) and imports back; Excalidraw and Mermaid export; Office/Visio-safe SVG option verified in PowerPoint, Word, Visio and Confluence.

### Round 8: import breadth, small modes, launch
- **A. Azure importers** (`types/azure`). Accept: Azure Resource Graph JSON, ARM/Bicep (`az bicep build` output), `terraform show -json`; groups by subscription/RG/VNet; merges and keeps pins; re-import after a change touches only changed elements.
- **B. Small modes on existing types** (`types/systems`, new `types/matrix`). Accept: threat overlay (trust boundaries, STRIDE per element/edge, generated threat table); DDD context-map edge kinds; generic `matrix` type with RACI and CRUD templates; share link (diagram in URL fragment, read-only viewer).
- **C. Docs site, template library, release** (`docs/site`, `.github`). Accept: gallery of every template, benchmark page vs Mermaid/D2-TALA/PlantUML (crossings, bends, displacement after one edit), "coming from" guides, npm publish pipeline, licence check, e2e over all templates.

### After round 8 (only on demand)
VS Code extension, comments sidecar, ERD importers (DDL/DBML/Prisma), Mermaid-style mind map on the tree engine, accessibility screen-reader outline in the editor beyond round 3, draw.io import of arbitrary diagrams. Revisit the order after the owner has used rounds 1–4 on a real client engagement.

### Changes against the gaps plan
- **Earlier:** model and views (R6 → R1), brand themes and icons (R2 → R1), new PPTX export (not planned before), sequence and roadmap (not planned before), editor craft (not planned before).
- **Later:** share link (R2 → R8), embed (R1 → R5), VS Code (R5 → after R8), comments (R8 → after R8), ERD importers (R5 → after R8).
- **Unchanged in intent:** MCP, Action with visual diff, stability, K8s, network, data wedge, access importers, steps, git flow, journey, interop, docs and launch.
